# Movement: Mover stack, input, networking

Paths under `Source/ZeroLock/`. Heroes are **Mover pawns, not ACharacters** (no CharacterMovementComponent).

## Stack
`AZeroLockCharacter` → `AZeroMoverPawn` (APawn + `IMoverInputProducerInterface`) → `UZeroMoverComponent` (`UCharacterMoverComponent`).
- Modes and transitions are configured in **Blueprint** (`Content/ZERO/monkeyBoi/BP_Mover_Monkey` MoverComponent; also `BP_ZeromoverPawn`, `BP_Deadlock_*`): modes `walking`, `falling`, `flying`, `sliding` (`UZeroSlideMode`), `melee` (`UZeroMeleeMode`), `ziplining` (`UZeroZiplineMode`), `locked` and `floating` (`UZeroFloatMode`); **component-level** transitions (checked every tick in every mode) `UZeroSlideTransition`, `UZeroMeleeTransition`, `UZeroZiplineTransition`. `StartingMovementMode` Falling.
- Per frame: Enhanced Input caches state on the pawn → `ProduceInput_Implementation` (fixed tick) writes `FCharacterDefaultInputs` + `FZeroMovementInputs` → `UZeroMoverComponent::OnMoverPreSimulationTick` applies layered moves / effects / mode queues → active mode simulates.
- Network prediction (`Config/DefaultNetworkPrediction.ini`): Fixed tick 60 Hz, simulated proxies Interpolated (100 ms buffer), `FixedTickInputSendCount=6`. Pawn `bReplicates`, `SetReplicatingMovement(false)`.
- **Facing and smoothing** (fixed 2026-10-25, the Deadlock heroes jittered a lot): Mover is the only owner of yaw. `bUseControllerRotationYaw` is **false** (C++ and all hero BPs), `ProduceInput` sends `OrientationIntent` = control **yaw only**, and `CommonLegacyMovementSettings.TurningRate` is **-1** (instant) on all seven hero BPs. Before that, the controller set the actor yaw every frame, the sim turned it toward the intent at 500°/s and wrote it back, and smoothing set the mesh from the sim's rotation, so the body shook whenever the camera turned. The MoverComponent's `SmoothingMode` `VisualComponentOffset` interpolates only the **mesh** between 60 Hz sim steps, which run before actor ticks. `AZeroMoverPawn::Tick` → `UpdateSmoothedCamera` (locally controlled) shifts the SpringArm by the same offset, ignoring offsets above 150 cm (teleports). Without it the camera stepped with the capsule. Actor rotation now changes only on sim steps, so code outside the sim that reads `GetActorRotation()` sees it up to one step (~16 ms) behind the camera. A new hero BP needs `TurningRate` -1 and controller yaw off.

## AZeroMoverPawn (`Mover/ZeroMoverPawn`)
- Capsule 34/88, mesh at (0,0,−88) yaw −90, SpringArm 400 (pawn control rotation) in C++.
- **Camera** (2026-10-25, matched to Deadlock): the `BP_Deadlock_*` heroes use each Deadlock hero's own `CitadelCameraSettings_t` (in the hero `.vmdl` keyvalues; dump with `Source2Viewer-CLI -i pak01_dir.vpk --vpk_filepath models/heroes_wip/<codename>/<codename>.vmdl_c -a` and grep it). 1 Deadlock unit = 2.54 × 0.7 (mesh scale) = 1.778 cm. Gravity: the world default (−980) except Solomon, whose MoverComponent has `bHasGravityOverride` with `GravityAccelOverride` (0, 0, −686) = 0.7 × (floatier; set on the BP, not by the importer). Values (arm Z / length / side, cm): Lash 75.6/182.6/64.7, Apollo (fencer) 70.2/183.1/67.6, Pocket 63.1/192/55.8, Solomon (chessmaster) 52.7/168.5/55.6, Doorman 72.6/183/70.9, Viscous 54.2/190.2/58.7. The importer sets this on new hero BPs (`apply_camera` in `Tools/DeadlockImporter/ue_import.py`; existing BP: `--camera-only`, Animation.md).
- **Per-hero speed** (importer `apply_movement`, with `--stats-only`): `CommonLegacyMovementSettings.MaxSpeed`, `StanceSettings.CrouchingMaxSpeed` and `UZeroMoverComponent::DashSpeed` on the BP = our tuned value × hero stat / Deadlock base hero stat (`config.json` `hero_setup.movement_reference`: walk 800 at `EMaxMoveSpeed` 7.2, crouch 200 at `ECrouchSpeed` 4.75, dash 1500 at `EGroundDashDistanceInMeters` 10), so Doorman (7.9) walks 878 and Solomon (6.7) 744 while the game's overall pace stays. A straight unit conversion would have been 7.2 m/s ≈ 504 cm/s at our scale. Static per BP, so predicted like any Mover setting; the `CurrentSpeed` attribute is still not wired (items use `MoveSpeedBonus`, see "Item stats"). No sprint (`ESprintSpeed`) and no separate air-dash distance. Not ported: per-hero crouch height (camera manager still drops a flat 45 cm; Deadlock's is 39–63 cm). Non-Deadlock BPs (`BP_Mover_Monkey` etc.) still use arm 400 + camera at (0,70,50), FOV 90.
- **Aim zoom** (alt fire default, GAS.md "Alt fire"): `AZeroMoverPawn::SetAimZoom(bZoom, FOVRelative, BlendTime)`, locally controlled only, `UpdateAimZoom` in `Tick`. Captures the camera FOV and arm length when the zoom starts and restores them exactly once it has blended out. FOV: base converted to Deadlock's 4:3 FOV (16:9 assumed), + `FOVRelative` (-40), back to 16:9 horizontal, so Deadlock heroes go 106.26 → 63.7 and FOV-90 BPs 90 → 44. Arm: `AimZoomArmLength` (Camera|Aim Zoom; Deadlock `m_flCameraBackOffsetAiming` × 1.778, written by the importer's `apply_camera`), or `TargetArmLength × AimZoomArmLengthScale` (0.65) when 0. Deadlock values (cm): Lash 131.3, Apollo 115.6, Pocket 113.3, Doorman 121.3, Viscous 115.6, Solomon 137.4 (set on all six `BP_Deadlock_*`). Smoothstep blend over 0.15 s.
- **Camera effects** (`UpdateCameraEffects`, locally controlled only, nothing in the sim): spring arm lag in Melee mode and for the first `ZiplineCameraLagTime` 0.4 s of a ride (`ActionCameraLagSpeed` 8, `ActionCameraLagMaxDistance` 150, eased over `ActionCameraLagBlendTime` 0.15 s). It skips the lag if the arm's lag is already on (Apollo's Itani) and restores the arm afterwards. Heavy melee zoom out: pulls back `MeleeZoomOutDistance` 100 from `MeleeZoomOutDelay` 0.1 s into the melee key hold (so light melee taps don't move it; the hold trigger is 0.5 s) through the end of the lunge, eased over `MeleeZoomBlendTime` 0.25 s. It moves `SpringArm.SocketOffset.X`, not `TargetArmLength`, so it doesn't fight the aim zoom.
- Input assets (BP): `DefaultMappingContext`, `MoveAction`, `LookAction`, `JumpAction`, `CrouchAction`, `DashAction`, `MeleeAction`, `ZiplineAction`. Melee and Zipline are bound on **Triggered**; `IA_Zipline` has a one-shot Hold trigger (0.25 s), so it fires once per press.
- **Space = jump and zipline** (`IMC_Default` maps `IA_Jump` and `IA_Zipline` to it). `OnJumpPressed` asks `UZeroMoverComponent::IsGrabbableZiplineInView` (the transition's look trace and refusals, not while riding): no cable in view jumps instantly; a cable in view holds the jump back (`bJumpHeldForZipline`). The grab starting clears it (no jump); releasing first, or a hold whose grab never started, sends the jump for one input frame (`bJumpTapQueued`), so a tap at a cable jumps on release. A press with no cable in view still jumps, then the hold can grab a cable you look at by then. The grab is only checked once, when the hold completes; it isn't retried.
- `OnJumpInputPressed` native multicast + `ConsumeJumpPress()` lets abilities swallow a jump (Pocket Barrage, EnchantersSatchel).
- `DeadlockAnimSet` (Animation.md).
- `GetSyncedAimRotation`, `GetInputWorldDir`: **buggy**, see issues.

## UZeroMoverComponent (`Mover/ZeroMoverComponent`)
`OnMoverPreSimulationTick` order: begin step (resim detection, stamina settings) → crouch intent from input (**before** `Super`, which applies the stance) → `Super` → rooted from input `bIsRooted` (+teleport, return) → exit `RootedModeName` on the unroot frame → (in `MeleeModeName` "Melee": no mantle/dash/jump) mantle (jump held, not while dashing; on success skips jump/dash only) → dash (costs stamina) → jump counter reset + air jump / wall bounce (skipped while a dash is active or this frame mantled/dashed) → slide-exit ease → ability linear move (Walking/Sliding → Falling) → dynamic move-to-actor → release → stop → pull → teleport. `HandlePostMovement` (bound to `OnPostMovement`) writes `FZeroMoverSimState` into the end sync state in the same step.
- **Prediction rules** (each was causing rollbacks in a recorded play session): read start-of-step velocity/location via `GetSimStartVelocity/Location()` (cached from the previous step's end state and on rollback; `GetSyncState()` is stale during resimulation and when several sim steps run in one frame). Use `IsResimulatingStep()` for cosmetics: the `TimeStep` given to the pre/post-sim hooks never has `bIsResimulating` set, so `GetLastTimeStep().bIsResimulating` is always false there. Facing inside the sim comes from `LookDir` (input), not the actor (actor yaw used to be set by the controller outside the sim and differed by up to 107° on the server; now the sim owns it, see Facing and smoothing). `bHandleJump` is off (the base class queued a second jump impulse on every ground jump).

**"Safe latch" API** (how gameplay code moves a pawn): `RequestSafeAbilityMove(Velocity, Duration)`, `RequestSafeDynamicAbilityMove(Actor, Duration)`, `RequestSafePullTo`, `RequestSafeStop` (100 ms zero), `RequestSafeRelease` (Locked → Falling), `RequestSafeTeleport`. Each sets a latch that the next `ProduceInput` copies into `FZeroMovementInputs`, so it is predicted. `ShouldIgnoreServerLatch()` makes the **server ignore these for remote-client-controlled pawns**: the owning client must make the same request.
Abilities also call `QueueNextMode("Locked"/"Falling"/FloatingModeName)` directly (Apollo ItaniLoSahn/Riposte, Lash DeathSlam, Pocket Barrage/EnchantersSatchel, `ZL_WaitChargeRelease_Task`). That isn't part of the predicted input stream.

## Data structs (`Mover/ZeroMovementData.h`)
- `FZeroMovementInputs` (custom NetSerialize): `LookDir`, `bWantsToCrouch`, `bCustomJumpJustPressed`, `bJumpHold`, `bWantsToZipline`, `bWantsToDash`, `bWantsToMelee`, ability move (velocity, duration), dynamic move (actor, duration), pull (target, duration), `bWantsStop`, `bWantsRelease`, teleport (target, `bTeleportSetsVelocity`, `TeleportVelocity`), `bIsRooted`, `bIsCubed`, `bIsGooBall`, `bIsFloating`, the four `Item*` stats. `MoveInput` and `bSlideIntentValid` are never used.
- Sync state: `FZeroMoverSimState{Stamina, AirJumpsUsed, AirDashesUsed, DashRemainingMs, bWasRooted, bWasSliding, MantleCount, MantleHeight, WallJumpCount}`. The last three are cosmetic uint8/float event counters for the anim, set through `Pending*` like the rest and **not** checked in `ShouldReconcile` (persistent type, added in the component ctor and again in `InitializeComponent` if a BP list lacks it), `FZeroMeleeSyncState{ElapsedTimeMs}`, `FZeroZipliningState{ZiplineActor, bMovingToEnd}`. `FZeroSlideState`, `FZeroDashState` unused.

- `AZero_BasePlayerController`: hero selection RPCs, `ShowDamageNumber` client RPC, projectile prediction helpers (Weapons.md), `OnPSInit`.
- `AZero_BasePlayerState`: replicated Kills/Assists/Deaths/TeamID/PlayerImage; UI VM refs.

- `AZero_ZiplineActor` (`Movement/`): spline (`GetZiplineComponent`); its collision must use the **Vehicle** object type (grab overlaps query it). `ZERO/Core/BP_BaseZiplineActor` draws the cable as cylinder instances along the spline. MoverExamples' `BP_Zipline` (in `L_CharacterMovementBasics`) is not one and can't be ridden.
- `FZeroZipliningState{ZiplineActor, bMovingToEnd, Distance, Speed, LastZipSimTimeMs}` is a **persistent** sync struct (component ctor + `InitializeComponent`). Mover removes every non-persistent sync struct at the start of each frame (`PrepareStateDataForNewFrame`), so before 2026-10-30 the ride state never survived a tick and the mode re-traced for its cable every step. Reconciles on actor/direction or Distance/Speed off by more than 10.
- Channel `ECC_GameTraceChannel1` = "Hero" (`DefaultEngine.ini:122`); pawn BPs must use the "Hero" profile for melee/weapon hits. `ECC_Vehicle` is reused as a line-of-sight / zipline channel.

## Known issues
- Slide: landing buffer unreachable (`ZeroSlideTransition.cpp:22`, `IsOnGround()` false in Falling; landing goes Falling → Walking → Sliding and needs ≥300 cm/s). Slide mode has no gameplay tags (`IsOnGround()` false while sliding), no floor/ledge check (keeps sliding in mid-air, air jumps keep resetting), no max duration; `SlideJumpImpulse` unused; header defaults disagree with ctor.
- `GetSyncedAimRotation` reads input from the sync state → always actor rotation (projectile aim has no pitch where used: `Zero_BaseWeaponAbility.cpp:36`, `ZL_Apollo_FlawlessAdvance.cpp:174`). Use `GetLastInputCmd()`.
- `GetInputWorldDir`: server returns zero for remote clients; local path includes pitch (`ZeroMoverPawn.cpp:283-299`).
- Prediction hazards: direct `QueueNextMode` from abilities (Apollo ItaniLoSahn/Riposte, Lash DeathSlam, Pocket Barrage, `ZL_WaitChargeRelease_Task`) runs at different sim frames on client and server, so every entry/exit causes a rollback. Route them through input the way `bIsRooted` works.
- One-shot input flags (`bCustomJumpJustPressed`, `bWantsToDash`, latches) are fragile: when the server is starved of input it re-runs the previous cmd (engine `NetworkPredictionService_Input.inl:146`, can repeat a jump/dash), and on buffer overflow it skips cmds (`:135`, can drop one). A request counter in the input plus a last-handled counter in `FZeroMoverSimState` would make them exactly-once.
- Stamina max/regen are read from GAS attributes each step; a replicated change lands on the client later than on the server (one correction). Effects that set the `Stamina` attribute directly are overwritten by the mover.
- Feel / rules (found 2026-10-11, not fixed): wall bounce is free and unlimited (no counter, no stamina) and its `BlockAllDynamic` sweep counts other pawns as walls; melee lunge ends with zero velocity (dead stop, drops straight down in air); no coyote time or jump buffer (a jump just after walking off a ledge is an air jump); jump in Float/Melee-like non-Walking/Falling modes counts as a free ground jump (Melee now blocked); mantle traces (`BlockAll`) hit pawns; slide entry boost has no cooldown (crouch-tap spam).
- Trust: the client decides `bIsRooted`, so a modified client can ignore roots.
- Choppy online movement = frame hitches, not the net code. On the server it shows as `LogNetworkPrediction: Gap in input stream detected on server` / `Recovering from input stream starvation`; on the client as `Invalid interpolation frames. Copying old content forward` (the 100 ms `FixedTickInterpolationBufferedMS` buffer runs dry). Seen 2026-10-19 with two uncooked `UnrealEditor.exe -game` instances on one PC, which compile shaders and load assets on demand. Judge smoothness on cooked builds or separate PCs (`stat unit`, `t.MaxFPS 60`) before raising the interpolation buffer or the input send count.
- The MoverExamples map teleporter (`L_CharacterMovementBasics` `TriggerVolume_10`) teleports outside the input stream, which causes large corrections. Example content only.
- Debug tool: `Saved/MoverRec/rec.py` (editor Python, `py "<path>" start|stop` during multiplayer PIE) logs per-frame pawn state, rollbacks and mode changes to CSV.
- Trust: latched moves aren't validated (except teleport distance). Server-only `RequestSafe*` on remote victims is dropped (`ZL_Lash_GroundStrike.cpp:170-177`, which also passes a displacement as velocity).
- Parry `DisableInput` can leave cached input stuck (stun no longer does: `ProduceInput` clears the cached move/jump/crouch/dash/melee/zipline input while `UZeroMoverComponent::IsStunned()` (`ZeroLock.Stun`), so stunned pawns don't move on their own; latched forced moves still apply). `CurrentSpeed` attribute doesn't affect Mover. Assist map never inserts (`ZeroLockCharacter.cpp:426-430`). `LastHitCharacter`/`AssistListCharacters` marked Replicated but not registered.
- `FZeroMovementInputs` is large and sent 6× per input. Game and editor targets disagree on build settings / include order.
